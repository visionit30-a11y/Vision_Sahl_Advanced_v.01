# ADR-0018: حد أمان الهوية والعضوية قبل سياق الجهة

- **الحالة:** معتمد للتنفيذ في Phase 2B — Group 1
- **التاريخ:** 2026-09-07
- **المرحلة:** Phase 2B
- **المرجع:** ADR-0014 إلى ADR-0017 وخطة Phase 2B المعتمدة

## السياق

تحتاج المصادقة إلى إثبات المستخدم وعضويته وحالة الجهة قبل إنشاء `TenantContext`. وفي
Baseline الحالي لا يقرأ `sahl_app` جدول `public.tenants`، وكل جدول يحمل `tenant_id`
يدخل حارس RLS في ADR-0016. وضع العضوية تحت سياسة الجهة المعتادة يصنع حلقة: يلزم السياق
لقراءتها، بينما يلزم إثباتها لإنشاء السياق.

## القرار

1. المستخدم هوية عالمية مستقلة عن Tenant. لا يحمل `auth.users` عمود `tenant_id`.
2. يدعم المستخدم عدة جهات عبر `auth.tenant_memberships` بعلاقة صريحة وفريدة بين المستخدم
   والجهة. لا role أو permission placeholder في Phase 2B.
3. جداول الهوية الجديدة تقع في مخطط `auth` ويملكها `sahl_migrator`.
4. `auth.tenant_memberships` جدول Identity-security عابر للجهات. يحتوي `tenant_id` الحقيقي
   ويأخذ **استثناءً واحدًا مسمى ومحدودًا** من عقد tenant-owned RLS.
5. الاستثناء لا يستبعد مخطط `auth`، ولا يغير اسم العمود، ولا يسمح بجداول أخرى. يبقى حارس
   اكتشاف `tenant_id` قائمًا، ويطبق على العضويات عقدًا بديلًا يفحص المالك والقيود والمنح
   ووظائف الوصول وعدم وجود بيانات أعمال.
6. لا تمنح `sahl_app` قراءة مباشرة على `tenant_memberships` أو `public.tenants`.
7. التحقق السابق للسياق يتم عبر وظائف PostgreSQL ضيقة يملكها المهاجر وتعمل
   `SECURITY DEFINER`. تستقبل session-token digest المستخرج في الخادم وmembership selector،
   ولا تستقبل user ID من العميل باعتباره إثباتًا.
8. تربط الوظيفة الجلسة بالمستخدم والعضوية والجهة، وتتحقق من صلاحية الجلسة ونسخ الأمان
   والحالات النشطة، وتعيد أقل قدر من الهوية المثبتة. لا تضبط GUC ولا تقرأ جداول أعمال.
9. الوظائف تستخدم SQL ثابتًا وأسماء مؤهلة، و`search_path` آمنًا مع `pg_temp` أخيرًا، وتسحب
   `EXECUTE` من `PUBLIC` داخل معاملة الإنشاء ثم تمنح التوقيع المطلوب فقط لـ`sahl_app`.
10. تنشئ طبقة Python مستقلة `AuthenticatedPrincipal`. لا يضاف actor أو session أو assurance
    إلى `TenantContext` المقفل.
11. يطبق `AuthenticatedTenantResolver` عقد `TenantResolver` على نتيجة تحقق موثوقة، ولا
    يستورد أو يورث `ExplicitTenantResolver`.
12. بعد ذلك فقط ينشأ `TenantContext` ويمر دون تعديل إلى `tenant_transaction(context)`.

## حالات الهوية المعتمدة

- المستخدم: `pending`, `active`, `suspended`, `archived`؛ الأرشفة نهائية.
- العضوية: `pending`, `active`, `suspended`, `left`.
- إنشاء سياق يتطلب مستخدمًا وجلسة وعضوية وجهة جميعها صالحة، وأن تكون حالات المستخدم
  والعضوية والجهة `active`.
- تعليق المستخدم يبطل جميع جلساته. تعليق العضوية يبطل اختيارها دون إبطال عضوياته الأخرى.
- لا جهة افتراضية دائمة؛ اختيار العضوية في الجلسة صريح.

## حدود الوصول

توجد وحدة DB خاصة بالهوية بمعاملات صريحة وعمليات typed محددة. لا تصدر `AsyncSession` أو
connection أو transaction handle إلى HTTP أو الخدمات. لا تستخدم `tenant_transaction`
قبل إثبات الجهة، ولا تضيف موضعًا ثانيًا لـ`set_config`.

تهيئة أول مستخدم وعضوية تتم بأداة تشغيل خارج HTTP. لا تسجيل ذاتي ولا دعوات أو إدارة أعضاء
عبر API قبل اعتماد Authorization/RBAC.

## النتائج والاختبارات الملزمة

- يلزم Migration وحارس catalog واختبارات سلبية مخصصة للاستثناء في Group 2/5.
- كل جدول جديد آخر يحمل `tenant_id` يبقى خاضعًا حرفيًا لعقد ADR-0016.
- تبقى `app.current_tenant_id()` و`public.tenants` ومنح runtime وعقود Phase 2A دون تغيير.
- رفض العضوية أو selector المزور يحدث قبل أي معاملة أعمال tenant-scoped.

## البدائل المرفوضة

- إنشاء السياق من header أو body أو query أو cookie أو subdomain.
- تغيير اسم `tenant_id` للتحايل على الحارس.
- منح قراءة مباشرة على جميع الجهات أو العضويات.
- إضافة سياسة واسعة أو `BYPASSRLS` أو Platform Tenant.
- تعديل `TenantContext` ليحمل هوية المستخدم أو صلاحياته.
