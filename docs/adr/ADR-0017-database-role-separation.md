# ADR-0017: فصل دور المهاجر عن دور التشغيل وحدود المنح

- **الحالة:** منفّذ في المجموعة الرابعة؛ Backend ‏222 passed مع نجاح حارس القاعدة بعد الاختبارات؛ القبول النهائي للمجموعة بيد المالك.
- **التاريخ:** 2026-09-07
- **المرحلة:** Phase 2A — الأدوار محليًا وفي CI
- **المرجع:** ADR-0014 إلى ADR-0016، واعتماد المالك Group 4 بعد قبول Group 3 عند `e91c30f`.

## السياق

مالك الجدول يستطيع تغيير RLS وسياساته، و`SUPERUSER` و`BYPASSRLS` يتجاوزانها.
لذلك لا يملك دور تشغيل التطبيق الكائنات التي يحميها RLS، ولا يستعير دور المهاجر أو دورًا
أعلى. `FORCE` وفصل الأدوار شرطان متكاملان.
[مرجع PostgreSQL 17 لـRLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html).

فصل عناوين الاتصال وحده لا يكفي إذا أعطت default privileges كل جدول جديد للتطبيق.
كانت إعدادات المشروع السابقة تمنح CRUD افتراضيًا لجداول المهاجر في `public`،
و`USAGE, SELECT` للتسلسلات، فأصبحت منح `tenants` أوسع من الحاجة التشغيلية.
قرار المجموعة الرابعة يسحب هذه المنح ولا يعوضها بسياسة tenant على جدول المنصّة.

## القرار

### 1. فصل الاتصالات والصلاحيات

| الجانب | العقد |
|---|---|
| `MIGRATION_DATABASE_URL` | `sahl_migrator` فقط، لـAlembic وتهيئة fixtures |
| `DATABASE_URL` | `sahl_app` فقط، للتشغيل ومحاولات الوصول في الاختبارات |
| المهاجر | يملك مخطط `app` والكائنات المنشأة في المهاجرات والجداول المملوكة لجهة |
| التطبيق | يملك صفر كائن؛ لا عضوية تتيح وراثة دور المهاجر |
| صفات التطبيق | `rolsuper=false`، `rolbypassrls=false`، `rolcreatedb=false`، `rolcreaterole=false` |
| إنشاء المخطط | `CREATE ON DATABASE sahl_dev` للمهاجر على قاعدة المشروع فقط؛ ليست صفة `CREATEDB` |
| DDL للتطبيق | لا ملكية أو صلاحيات تتيح CREATE أو ALTER أو DROP أو إنشاء/تغيير سياسة |
| استعمال الدالة | `USAGE` على `app` و`EXECUTE` على `app.current_tenant_id()` بحسب 0003 |
| `public.tenants` | لا SELECT أو WRITE للتطبيق أو PUBLIC، ولا tenant RLS |
| probe أثناء fixture | SELECT وINSERT وUPDATE وDELETE الضرورية فقط على الجدول نفسه |

لا fallback من عنوان المهاجرات إلى عنوان التشغيل. يرفض Alembic دور التطبيق قبل المهاجرات؛
لا فحص دور يترك معاملة ضمنية تتراجع وتلغي المهاجرات عند غلق الاتصال. تفشل البوابة عند
خطأ المهاجرة، وتتحقق من head الفعلي قبل اختبارات القاعدة. هذه إصلاحات المجموعة الثانية
المقبولة، ويحافظ عليها تنفيذ المجموعة الرابعة.

لا منح `ALL PRIVILEGES` للتطبيق على probe، ولا `TRUNCATE` أو `REFERENCES` أو
`TRIGGER` أو grant option. RLS ليس حماية لعمليات مثل TRUNCATE على الجدول كله،
لذلك لا تُمنح أصلًا.
[حدود عمليات RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html).

### 2. إغلاق المنح القديمة بمهاجرة مستقلة

اسم المهاجرة الرابعة هو **`0004_runtime_privilege_boundary`** بعد
`0003_tenant_context_function`. تحل محل الاسم المخطط سابقًا
`0004_tenant_isolation_policies`: بعد قرار إبقاء `tenants` خارج tenant RLS،
لا توجد سياسة إنتاج تنشئها هذه المجموعة.

`upgrade` يسحب منح الجدول القديمة من `sahl_app` و`PUBLIC` على `public.tenants`،
ويزيل default grants الواسعة للتطبيق على جداول وتسلسلات المهاجر في `public`.
لا ينشئ جدولًا أو سياسة أو probe أو دالة أو تسلسلًا، ولا يغير بيانات الجهات.
تُحدّث التهيئة المحلية وCI أيضًا كي لا تعيد هذه المنح عند إنشاء بيئة جديدة.

`downgrade` يعيد عقد المنح المعروف عند 0003: CRUD للتطبيق على `tenants`،
وCRUD الافتراضي لجداول المهاجر في `public`، و`USAGE, SELECT` الافتراضي للتسلسلات.
هذه عودة إلى حالة المهاجرة السابقة لغرض العكس والاختبار؛ ليست حالة تشغيل مقبولة
للمجموعة الرابعة، ولا محاولة لاسترجاع أي ACL مخصص خارج عقد المشروع.

Default privileges تؤثر في الكائنات الجديدة لدور الإنشاء، ولا تسحب حقوق الجداول
الموجودة؛ لذلك يتضمن الإصلاح السحب من `tenants` والسحب من default ACL معًا.
[مرجع PostgreSQL 17 لـALTER DEFAULT PRIVILEGES](https://www.postgresql.org/docs/17/sql-alterdefaultprivileges.html).

### 3. الحراس المطلوبة

المرجع هو كتالوج PostgreSQL والامتياز الفعلي، لا نص ملفات SQL وحده:

- أعلام الأدوار وعضوياتها لا تتيح تصعيد runtime إلى مالك أو دور يتجاوز RLS.
- `sahl_app` يملك صفر كائن في قاعدة المشروع؛ كائنات الجهات مالكها `sahl_migrator`.
- يُفحص عدم CREATE للتطبيق وعدم grant option أو منح عامة تتجاوز المنح الضرورية.
- `tenants` بلا امتياز SELECT أو كتابة للتطبيق، وبلا سياسة tenant أو عمود `tenant_id`.
- لا default grants واسعة على جداول وتسلسلات المهاجر، سواء أعادت التهيئة إضافتها أم لا.
- حارس RLS يكتشف الجداول ذات `tenant_id` آليًا ويتحقق من العقد في ADR-0016.

لا يعتمد الحارس على غياب كائن الاختبار بعد teardown وحده: يفحص العقد أثناء وجوده،
ثم يثبت عدم بقائه بعد الاختبار. فشل أي حارس يمنع قبول البوابة.

### 4. مسؤول المنصّة مستقبلًا

Platform Admin دور أعمال مستقبلي لا صلاحية PostgreSQL لتجاوز RLS. لا `BYPASSRLS`
ولا تعطيل سياسة ولا تشغيل HTTP ببيانات المهاجر. أي قراءة مستقبلية لجدول المنصّة
تحتاج حاجة تشغيلية وتفويضًا ومنحًا معتمدة في مرحلتها؛ لا تمنحها هذه المجموعة استباقيًا.

## التحقق وإجراء الإغلاق

نجح Backend كاملًا: **222 passed** على PostgreSQL 17 الحقيقي مع `--strict-security-gates`،
منها 153 اختبارًا سابقًا و69 جديدًا: 53 اختبار قاعدة و16 اختبار وحدة، بتقسيم §14 من
خطة Phase 2A. تشمل الإثباتات الجديدة
[test_rls_runtime_ddl_denial.py](../../apps/api/tests/db/test_rls_runtime_ddl_denial.py)
وحراس المنح والملكية. نجح حارس القاعدة بعد pytest: لا آثار probe، وصفر جداول إنتاج
مملوكة لجهة. نجحت أيضًا 25 حالة لاختبار تنسيق بوابات PowerShell.

يرفض نمط `--strict-security-gates` نتائج pytest الفعلية SKIP وXFAIL وXPASS.
حارس `tests.db.verify_clean_database` مستقل بعد pytest ويعمل حتى عند فشلها؛
محليًا ضمن `03-test.ps1` وفي CI بخطوة `if: always()`. فشله blocking.

إجراء الإغلاق يشمل دورة المهاجرة العكوسة ثم التحقق من head، وتشغيل `03-test.ps1`
بكامل 17 بوابة. يسجّل التقرير الختامي نتيجته ومسار السجل والتحقق المباشر من الأدوار
والمنح والملكية وhead وغياب probe وآثارها؛ لا تُفترض نتيجة البوابة الشاملة من Backend.
لم يُنفّذ CI بعيد للمجموعة الرابعة عند تسجيل هذه النتيجة؛ أي تشغيل لاحق يوثّق بـrun
والـcommit المختبَر. قبول المجموعة النهائي يحتاج مراجعة المالك.

BRD وSRS لا يتغيران. لا إضافة Docker أو OCI أو Terraform أو خدمة تفويض أو Phase 2B.
